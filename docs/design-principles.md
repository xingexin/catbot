# catbot 设计理念与开发约束

catbot 的主体是可持续运行的对话和任务框架。QQ、模型厂商、插件语言与部署方式都是可替换的外部能力。代码组织需要让领域规则能单独验证，让一次对话、任务和通知的完整执行过程可追踪、可恢复。

这份文档说明项目的长期设计要求。仓库根目录的 [AGENTS.md](../AGENTS.md) 是开发及代码审查时应遵循的精简约束；现有实现的通信与恢复边界见 [architecture.md](architecture.md)。

## 1. 规则有归属，编排有边界

| 层 | 负责什么 | 不应负责什么 |
| --- | --- | --- |
| `domain` | 会话上下文规则、人格组装、工具授权、任务合法性、状态转换、领域仓储 | 直接发 HTTP、启动进程、操作 SDK 或依赖 transport |
| `biz` | 加载数据、调用规则、安排事务和副作用、保存结果，组合一次完整用例 | 包办所有校验、协议解析、基础设施实现 |
| `infra` | PostgreSQL、模型协议、SDK 桥接、文件、消息适配器、Temporal、插件进程 | 决定用户业务行为或反向依赖 biz |
| `transport` | 鉴权、入参校验、序列化、HTTP/SSE/MCP 协议转换 | 直接编排任务步骤、决定业务状态转换 |
| `worker` | 队列驱动、Workflow/Activity 注册、恢复扫描和运行生命周期 | 复制 biz 的状态规则 |
| `bootstrap` | 依赖构造、注册、注入、启动和关闭 | 演变成新的全能 App |

实体保留能够提高内聚性的行为，复杂规则可以使用领域服务或纯函数。简单查询直接使用对应领域仓储。当前 `domain/*/repository` 复用 `infra/store` 的通用 JSONB 底座，底座不反向引用领域；这是现有工程的明确边界，不要求为每一个简单模块创建大量接口和子目录。

同一条规则应只有一个实现。例如，任务是否允许执行由任务领域及对应应用服务决定，Web、聊天工具和 Temporal Activity 都调用它，而不是各写一份判断。

## 2. 所有有限业务分类采用整型枚举

### 为什么这样规定

直接比较 `"running"`、`"binary"` 或 `"onebot"`，容易让同一分类的拼写散落到各层，无法在编译阶段发现不同类型混用，也难以完整审查新增状态的处理分支。具名整型枚举把可选值收敛到所属领域，提供集中校验及转换入口。

规则适用于业务类型、状态、操作、执行策略等有限集合。ID、用户消息、邮箱地址、模型名称、插件工具名称属于开放数据，仍然使用字符串。枚举并不要求把所有字符串都改成数字。

### 定义方式

```go
// Resource 的编号已进入 API 契约，不得重排或复用。
type Resource int

const (
    ResourceUnknown Resource = 0
    ResourceSession Resource = 1
    ResourceTask    Resource = 2
)
```

业务代码使用具名常量：

```go
switch resource {
case ResourceSession:
    return archiveSession(ctx, id)
case ResourceTask:
    return archiveTask(ctx, id)
default:
    return ErrUnknownResource
}
```

不使用 `type Resource string`，也不使用 `resource == 1`、`record["type"] == "session"` 这样的业务分支。前端使用对应的 numeric enum；页面名称通过 label 映射展示，不把用户可见文案当作类型标识。

稳定编号的规则是：

1. `Unknown = 0`，缺省值不是有效业务选择。
2. 持久化、API 和跨进程枚举显式赋值，不用 `iota` 使后续插入改变编号。
3. 已使用编号不得重排或复用。废弃值保留编号，并在入口明确拒绝或提供兼容转换。
4. API 和配置入口校验未知值；不能把未知值静默解释为某个默认提供商或成功状态。
5. 业务分支只比较具名枚举。输入格式转换与展示 label 映射集中维护。

归档功能使用三组独立类型，避免混用资源与操作编号：`Resource` 表示对话、任务等资源，`Action` 表示归档、恢复、永久删除，`RecordState` 表示活动、归档。具体固定编号以 `internal/domain/lifecycle/lifecycle.go` 为准。

### 字符串协议的兼容边界

第三方 API、MCP 协议及已经保存的 JSON 可能使用字符串。保留这些外部协议，在适配器或编解码边界转换成内部枚举：

```text
旧 JSON / 第三方字符串 → 显式解析、校验 → 领域 int 枚举 → 业务规则
领域 int 枚举 → 显式编码映射 → 兼容旧 JSON / 第三方字符串
```

转换函数可以判断字符串，因为它正是边界转换的位置；业务规则不再重复判断原始字符串。外部未知状态转换失败时应返回错误，尤其不能把无法识别的执行状态视作“已完成”，进而允许删除或重新发送。

**迁移现状：此次新增归档契约使用整型枚举，但历史任务、运行、插件和模型代码仍有字符串状态与协议字段。没有在本次对全仓 wire 格式做一次性替换。** 后续迁移按领域进行：盘点持久值和调用方，定义固定枚举与兼容编解码，调整业务分支，再运行旧记录读取、API、SDK、插件和 Temporal 历史回归测试。未经迁移与验证，不能宣称历史代码已经全部符合新规范。

## 3. 删除分为归档与永久删除

### 归档与恢复

普通列表的删除入口先归档。原始记录及其关联内容保留，默认列表过滤归档项；归档栏集中提供恢复和永久删除。归档索引只保存资源类型、原始 ID、显示名称和归档时间，不复制消息正文、人格提示词或凭证。

恢复保留原 ID、内容和关联关系，但不自动恢复会产生外部动作的能力：任务恢复后保持暂停，插件恢复后保持停用。用户需要显式恢复运行，避免在整理归档时意外触发消息、邮箱操作或定时任务。

### 永久删除的条件和范围

永久删除只允许来自归档栏的记录。删除前检查活动执行、待处理通知、默认配置、会话、任务和其他实际引用；有阻塞依赖时返回具体原因，而不是把关联配置一并清空。对于结果不明的外部操作，不能把“没拿到结果”当作安全完成。

目标拥有的正文、运行事件以及对应附件需要真正清除，不是再次设置一个隐藏标记。共享内容及仍被其他记录引用的配置应阻止删除或保留，不盲目连带删除。删除范围是本服务拥有的业务记录、关联事件及附件。删除本地会话不会撤回已经发到 QQ 的消息，也不清除 SDK 厂商原生会话、独立执行服务日志或 Temporal 保留的历史；这些存储有独立的生命周期。本功能不等同于跨服务数据擦除。

数据库记录与运行事件使用同一事务删除，任一步骤失败则整体回滚。文件系统不与数据库共享事务：附件删除失败保留归档元数据以便重试；删除文件成功但数据库提交失败时，也要允许安全重试，不能报告全量成功。检查与写操作使用与提交、执行相容的业务锁，避免检查后产生新的引用。

### 允许保留最小防重放墓碑

某些记录对应稳定操作 ID。完全忘掉该 ID 后，晚到的 Worker、重复平台事件或重试请求可能把已经删除的操作当作新操作，重新创建任务或发送消息。因此硬删除可以在同一事务中保留仅含记录类型、ID、删除时间的墓碑。

墓碑不保留正文、用户提示词、结果、收件人或凭证明文。关键写入口检查墓碑，已清理的操作不能重新执行。该机制用于防重放，不把墓碑当作归档内容的替代存储，也不承诺外部系统绝对只执行一次。

批量操作按每条记录返回成功与失败。一个目标自身的级联删除必须原子完成，但整批中一项失败无需掩盖其他已成功项；管理端保留失败项并显示原因。

## 4. 插件依赖协议，不绑定语言

Go 插件编译成独立可执行文件，TS/JS 插件通过 Node 运行。当前二者都是 catbot 启动及管理的独立子进程，核心通过 **MCP over stdio** 发现工具、传入参数和获取结果。MCP 使用 JSON-RPC 消息，标准输入和标准输出承载协议，标准错误承载日志。

插件调用宿主提供的存储、模型、任务、附件和通知能力时，使用经过鉴权及权限检查的 **HTTP API**。插件不需要依赖某家 Agent SDK，也不需要导入 Go 核心内部业务包。

```text
catbot 主进程 ── MCP stdio ──> Go / Node 插件子进程
catbot 宿主 API <── HTTP ───── 插件 SDK
```

独立进程提供内存和生命周期上的分离，**当前不代表每个插件拥有独立容器、文件系统权限或资源配额**。Docker 部署时插件与核心通常在同一个后端容器；如需更强隔离，要额外设计容器、权限、网络和资源限制，不能把进程隔离直接称为安全沙箱。

插件权限由服务端检查，人格只能缩小工具范围；固定版本和快照保证已启动任务不随插件配置修改而改变。稳定操作 ID 贯穿工具调用、任务与通知；副作用结果不明时保留不确定状态，不盲目重跑。

## 5. 可验证性是交付的一部分

新增功能需要验证正常流程、无效枚举、未知边界值、权限拒绝、并发竞争、部分失败、事务回滚和恢复行为。纯规则通过单元测试验证；跨进程、存储事务和恢复流程通过相应集成测试验证。

真实 PostgreSQL 测试必须使用专用测试数据库和隔离 fixture。真实 QQ、邮箱或模型联调与模拟协议测试分别记录，不用模拟通过替代真实兼容性结论，也不通过删除生产数据验证永久删除。

每次改变枚举、协议或状态转换，都应说明旧记录如何读取、已启动任务如何继续、重试如何避免重复副作用，以及尚未验证的边界。

### 工具缓存与硬删除边界

新工具调用会显式记录运行或执行记录与最终缓存键的归属；硬删除同时清理明确归属的 `operation`、`tool-result` 和 `tool-started` 缓存，共享缓存仅在最后一个归属被删除时清理。对缺少归属索引的历史数据，只使用执行快照中的工具步骤键，或 SDK 工具事件中可证明的实际调用键；旧 API 工具事件、自定义键及其他无法确认归属的历史缓存不会猜测删除。此兼容边界意味着历史正文可能仍存在于无法识别归属的旧缓存。SDK 原生会话目录、Temporal 外部历史及已发到外部平台的消息不由本地记录硬删除跨服务抹除。
