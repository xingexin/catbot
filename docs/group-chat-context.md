# 群聊记录、上下文与总结

catbot 将群消息记录和 Agent 会话分开。指定群的普通消息经验签、群授权和去重后落库；没有 @ 机器人时不创建 Run、不调用模型、不自动回复。@ 仍进入原来的按用户隔离会话。

## 在管理端启用

进入「系统与凭证 → 个人 QQ · OneBot 通道」，在 OneBot 配置中：

1. 保持正确的机器人账号、允许群号、模型配置与群聊人格。
2. 开启「群聊记录」，明确选择采集群。空列表不表示全部群。
3. 设置保留天数（1–365，默认 7）、自动附带近期条数（0–100，默认 30）和每群保留条数（100–100000，默认 10000）。近期条数设 0 只关闭自动附带，仍可按需查历史。数量清理采用固定 100 条的余量：设置 10000 时可保留至 10099 条，达到 10100 条一次裁剪回 10000 条；主动调低保留条数会立即裁剪至新值。
4. 在所用群人格的工具清单中加入 `system__group_history`，然后保存。人格为空工具列表时仍可获得管理员开启的近期上下文，但不能查询更多历史。

旧部署的采集默认关闭。旧客户端保存绑定时省略 `groupHistory` 字段，会保留原有采集设置。开启采集只对已授权并选中的群生效；移除允许群、关闭通道或关闭采集后立即拒绝新采集及历史查询，不会扩大联系人、任务、邮箱或其他插件权限。

## 使用示例

- 群员正常讨论，不需要 @。
- `@catbot 刚才大家说的交付时间是什么？`：自动附带一小段近期群消息。
- `@catbot 总结今天群里的讨论，列出结论和待办。`：Agent 可以调用历史工具，按时间、关键词、发送者和游标分页读取。
- 需要定时群日报时，通过现有任务创建一个 Agent 步骤，绑定该群来源会话、模型和允许历史工具的群人格，设置时间、时区与通知。任务仍受发起人的会话权限控制。

基本问答和总结适用于 API 直连与三个 SDK 适配器。SDK 恢复原生会话时也会收到本轮群参考资料。更长的分段总结可以启用独立的 [`group-chat` 插件](../plugins/group-chat/README.md)；该可选插件通过宿主模型能力生成摘要，需要 API 模型配置和 `models` 授权。

历史工具参数为 `startTime`、`endTime`（带时区的 RFC3339）、`limit`（1–100）、`cursor`、`keyword`、`sender`（发送者 ID）。返回 `history.messages`、`history.hasMore`、`history.nextCursor` 和覆盖信息。分页时保持原查询条件。工具不接受账号或群号，目标群由服务器从执行来源会话推导。

## 数据和权限边界

- 共享群记录按通道、机器人账号、群号隔离；个人 Agent 会话继续额外包含发言人 ID。
- 保存消息 ID、发言人 ID/显示名、平台时间、方向及文本；保存成功发送的机器人回复，发送失败或结果不明不标记为已发生的群发言。
- 普通文本采集不调用模型。图片、语音、视频等仅记录未解析标记，不能据此总结媒体内容。
- 群资料作为本轮参考信息传入，不写入个人 `Session.Messages`，也不覆盖人格提示词。SDK 可能在其原生会话中保留已注入的资料，模型先前生成的回答也可能包含摘要；群记录的保留期不等同于清除 SDK 或模型侧数据。模型收到的引用内容不构成创建任务、发送通知或读取私人数据的授权。
- 同一轮的历史截止时间固定在触发消息的时间；后台任务使用该次运行创建时间。运行期间新来的消息不会改变该轮查询的截止范围；这是按平台时间筛选，不是数据库快照，延迟送达且时间早于截止点的消息仍可能进入后续分页。
- PostgreSQL 使用独立的 `time_series_scopes`、`time_series_entries` 表，按群范围和时间索引分页；同一范围内的平台消息 ID 幂等。每条消息实时入库，不使用内存写入队列或 Redis。数量达到保留目标加 100 时批量物理清理至目标；重复 ID 不增加条数。过期消息按保留天数独立清理，不等待凑满 100 条，查询也强制过滤过期数据；后台每 15 秒进行一次清理，停用采集后仍清理过期内容。近期上下文继续直接按索引查询数据库。
- 群消息不属于某一位用户的私人会话，归档或删除单人的对话不会同时清空整个群的公共记录。

## 完整性与限制

目前只查询本系统实际收到并保存的消息，没有自动向 NapCat 补拉上线前的记录。停机、QQ 离线、平台漏推送、暂停采集、保留期或条数上限都可能造成缺口。覆盖信息中的采集起点和可用时间范围不等同于已证明连续完整；总结必须说明实际范围，不能称为全量聊天。

单条消息正文最多保存 16 KiB，截断会标记；自动上下文页最多 8 KiB，历史工具页最多 48 KiB，API 直连时还会按本轮工具结果预算收紧页面，保留分页游标；过小预算明确返回错误。超过范围需分页。上下文及整个 API 请求还有独立输入预算，失败会明确返回，不静默跳过。

未来其他消息框架仍可提供相同接收契约；平台历史补拉可以通过独立的可选 HistoryReader 接口扩展，无须改变 Agent 会话或 Sender。

## 验证

新增自动化覆盖包括：未 @ 入库且零 Run、并发消息去重、同群不同人的公开发言可读、不同群/账号及私聊不可读、关闭采集立即失效、运行固定截止时间、原私人会话和任务权限保持隔离、API/SDK 请求包含群上下文、SDK native resume 注入、分页/保留期/条数和字节上限、管理端配置校验。

自动化接口和 SDK 模拟验证不代表真实平台联调；真实 QQ 与供应商端点需在实际登录与凭证可用时分别验证。

### 数量批量裁剪验收

- 消息继续逐条实时入库；近期上下文继续从 PostgreSQL 读取。没有增加内存队列、Redis 或新的数据库字段。
- 默认目标 10000 条：专用测试库批量构造 10099 条真实记录，重复消息、重复配置及后台清理均保留 10099 条；重开 Store 后收到第 10100 条，物理记录变为 10000 条且最旧 100 条被删除。
- 目标 100 和 137 的同一套 Memory/PostgreSQL 契约覆盖下一轮阈值、并发去重、跨通道/账号/群隔离、过期清理、主动降低目标。裁剪失败时新增消息与删除操作整体回滚，重试同一 ID 可以完成。
